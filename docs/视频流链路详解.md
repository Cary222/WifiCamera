# 相机视频流 USB / WiFi 双链路通用架构详解

本文说明：**一类 WiFi 相机设备的画面，如何从传感器经过编码、RTSP、MediaMTX 和 WebRTC，最终到达 Android App、MuMu 模拟器或手机**。

本文主体描述的是可复用的架构和协议，不把某一块板子的序列号、MAC、SSID 或 IP 当成固定条件。文中的端口是本项目参考实现的默认端口；换板、换固件或换网络拓扑时，应以设备实际配置为准。

文末和“本项目实例”小节保留了当前环境的具体参数，用于复现和排查，不代表所有设备都必须使用这些值。

## 一、本项目实例更新记录：USB 与 WiFi 双链路已经打通

> 本节只记录当前项目这块设备的部署结果。通用原理请看后面的“共同核心与逐包原理”章节；换设备时不要直接复制本节的 IP、SSID、MAC 或序列号。

### 1. App 新增链路选择

设置页新增：**设置 → Wi-Fi 设置 → 连接方式**：

- **自动**：并行探测 USB 与 WiFi，选择能回应 `/status` 的链路；
- **USB**：固定使用 MuMu 宿主机的 USB/ADB relay 链路；
- **WiFi**：固定直连板端热点，不经过 USB relay。

当前 App 不再把地址在启动时固定死。相机 HTTP、WebSocket、WHEP 和图片请求都会根据当前链路动态解析地址。

```text
USB:
  控制 http://10.0.2.2:18999
  视频 http://10.0.2.2:18787/board-webrtc/cam0/whep

WiFi:
  控制 http://192.168.1.1:8999
  视频 http://192.168.1.1:8889/cam0/whep
```

### 2. 两条视频链路的实测结果

| 项目 | USB 链路 | WiFi 链路 |
|---|---|---|
| 控制 | `10.0.2.2:18999` | `192.168.1.1:8999` |
| WHEP 信令 | 主机 relay `18787` | 板端 `8889` 直连 |
| WebRTC 媒体 | relay UDP `18189` + USB 隧道 | WiFi UDP 直连板端 `8189` |
| ADB forward | 需要 3 条 | 不需要 |
| relay | 需要 | 不需要 |
| 预览 | 正常 | 正常 |
| 实拍照片 | `1920x1080` | `1920x1080` |

WiFi 实测时已关闭 relay，并清空三条 ADB forward；App 仍然可以预览和拍照，因此确认不是“WiFi 走了 USB relay”，而是真正的板端 WiFi 直连。

### 3. WiFi 热点同名问题已处理

发现两块板都使用 `SC311-1234567` 和 `192.168.1.1`，Windows 会错误连接到信号更强的旧板。目标板的无线 MAC 是：

```text
目标板：88:49:2D:54:95:05
旧板：  fc:37:6D:E7:1B:96
```

已将目标板的启动脚本 `/root/start.sh` 中的热点名称固定为：

```text

```

这样板子重启后也不会恢复成重复的 `SC311-1234567`。密码仍为 `12345678`。目标板通过该 SSID 获取主机地址 `192.168.1.50`，板端地址为 `192.168.1.1`。

### 4. 自动切换的防抖规则

自动模式不是一断线就切换：

1. 控制通道离开 `open` 持续约 5 秒才重新探测；
2. 两次探测至少间隔 5 秒；
3. 探测期间不重复进入；
4. 只有另一条链路真实回应 `/status` 才切换；
5. 切换会先关闭旧控制连接，再重建 WebSocket 和 WHEP 会话。

这样可以避免 USB 瞬时重新枚举时在 USB/WiFi 之间来回跳转。自动切换逻辑已实现，双链路本身已实测，断线后的自动切换尚未单独做完整验收。

## 二、一句话回答

两条链路的视频**本质上都是 WebRTC**，信令使用 **WHEP**，板端都先把传感器画面编码成 H.264，再由 MediaMTX 把 RTSP 源转换成 WebRTC。

区别只有 WebRTC 媒体包离开板子的方式：

- USB：WebRTC 的 UDP 包被 relay 和板端隧道包装进 TCP，穿过 ADB/USB；
- WiFi：WebRTC 的 UDP 包直接通过板端热点到 App，不经过 relay 和 ADB。

因此，**USB/WiFi 不是两套不同的视频协议，而是同一套 WebRTC 视频在两种底层传输路径上的实现**。

## 三、两条路的共同核心与逐包原理

### 1. 两条路共用的板端视频生产流程

无论 App 选择 USB 还是 WiFi，板端前半段完全相同：

```text
IMX662
  ↓
V4L2 sensor window / ROI
  ↓
VI（视频输入）
  ↓
VPSS（视频处理）
  ↓
VENC（H.264 硬件编码）
  ↓
RTSP 服务器 :554/live/0
  ↓
MediaMTX 读取本地 RTSP
  ↓
MediaMTX 通过 WHEP 创建 WebRTC 会话
  ↓
App 的 react-native-webrtc 解码并显示
```

这里有一个容易误解的点：**App 并不直接接收 RTSP**。RTSP 只在板端内部作为 MediaMTX 的输入源，App 最终接收的是 WebRTC 的 RTP 媒体包。

所以端口 `554` 不需要暴露给 App，也不需要做 ADB forward；真正给 App 使用的是 WHEP 信令端口 `8889` 和 WebRTC 媒体端口 `8189`，USB 模式则通过 relay/隧道间接使用它们。

### 2. WHEP 握手的共同流程

两种链路的 WHEP/ WebRTC 协商步骤相同，只有 URL 和 ICE candidate 地址不同：

```text
App                                      MediaMTX
 │                                           │
 │ ① 创建 RTCPeerConnection                  │
 │   recvonly video + audio                  │
 │   createDataChannel                       │
 │                                           │
 │ ② POST SDP offer /cam0/whep ────────────> │
 │                                           │ 读取 RTSP 源（sourceOnDemand）
 │                                           │ 创建 WHEP session
 │ ③ <──────────── SDP answer + Location     │
 │                                           │
 │ ④ setRemoteDescription(answer)            │
 │                                           │
 │ ⑤ PATCH trickle ICE candidates ─────────> │
 │                                           │
 │ ⑥ ICE candidate pair nominated            │
 │                                           │
 │ ⑦ <════════════ RTP/H.264 视频包 ═══════ │
 │ ⑧ <════════════ RTCP 统计/反馈 ════════ │
```

`WHEP` 主要负责**用 HTTP 完成 SDP 会话建立**，不是把整段视频放在 HTTP 响应里。握手结束后，视频由 WebRTC 的 RTP/RTCP 通道承载。

### 3. USB 路：为什么要把 UDP 塞进 TCP

USB 模式下，App 先访问**模拟器看到的宿主机地址** `<EMULATOR_HOST_IP>`。在 MuMu 的当前部署中，这个占位符对应 `10.0.2.2`；其他模拟器或真机调试环境可能使用不同地址。

ADB forward 能做的是 TCP 端口转发：

```text
App TCP <EMULATOR_HOST_IP>:<USB_CONTROL_PORT>
  └─ ADB forward ─→ 板端 TCP :8999

App HTTP <EMULATOR_HOST_IP>:<RELAY_HTTP_PORT>
  └─ 主机 usb-webrtc-relay
       └─ TCP 127.0.0.1:<USB_WHEP_FORWARD_PORT>
            └─ ADB forward ─→ 板端 HTTP :<BOARD_WHEP_PORT>
```

本项目示例值为：`<EMULATOR_HOST_IP>=10.0.2.2`、`<USB_CONTROL_PORT>=18999`、
`<RELAY_HTTP_PORT>=18787`、`<USB_WHEP_FORWARD_PORT>=18889`。

但是 WebRTC 媒体通常使用 UDP，不能直接通过 `adb forward tcp` 穿过 USB。因此 USB 路的媒体包分成下面几步：

#### USB 路：板端 → App（视频下行）

```text
① MediaMTX 在板端 127.0.0.1:8189 产生 WebRTC RTP/RTCP
        ↓ UDP
② board_webrtc_udp_tunnel 收到 UDP 包
        ↓ 加 4 字节大端长度前缀
③ 隧道把 [长度][UDP payload] 写入 TCP :18190
        ↓ ADB forward tcp:18190→tcp:18190
④ Windows 主机 relay 的 TCP socket 收到字节流
        ↓ 去掉长度前缀，还原 UDP payload
⑤ relay 从 UDP `<RELAY_UDP_PORT>` 发给 `<EMULATOR_HOST_IP>` 上的 App
        ↓ WebRTC ICE/RTP
⑥ react-native-webrtc 收 RTP，交给 Android 硬解
        ↓
⑦ PreviewSurface / RTCView 显示画面
```

#### USB 路：App → 板端（反馈/控制方向）

视频接收主要是板端到 App，但 ICE、RTCP、连接探测等存在反向数据：

```text
App → `<EMULATOR_HOST_IP>:<RELAY_UDP_PORT>` UDP
  → relay 按 App 的 address:port 建立会话
  → 加 4 字节长度前缀写入 TCP
  → ADB forward 到板端 :18190
  → board_webrtc_udp_tunnel 拆帧
  → 发送到板端 MediaMTX :8189 UDP
```

relay 会按每个 App 的 UDP 来源建立会话，隧道刚建立时最多缓存 64 个 UDP 包；超过 8 秒没有流量的会话会清理。

#### USB 路的 SDP 为什么必须改写

板端 MediaMTX 只能知道设备侧地址，例如 `127.0.0.1` 或 `<BOARD_IP>`。如果把这些地址原样放进 USB 模式的 SDP，模拟器里的 App 可能会访问自己的回环地址或错误网段，无法把媒体包送到主机 relay。

所以 relay 在 HTTP 反代 WHEP answer 时，把 UDP host candidate 改成**模拟器可达的宿主机地址和 relay UDP 端口**：

```text
a=candidate:... udp ... <EMULATOR_HOST_IP> <RELAY_UDP_PORT> typ host
```

本项目示例为 `10.0.2.2:18189`。

这一步把“App 应该把 WebRTC UDP 发到哪里”明确指向主机 relay。TCP candidate 在当前 USB 方案中被删除，避免 App 选到无法工作的路径。

#### USB 路需要的三个 forward

```text
18999 → 8999    控制 WebSocket/HTTP
18889 → 8889    WHEP HTTP 信令
18190 → 18190   UDP-over-TCP 媒体隧道
```

少任何一个都会出现不同故障：控制、信令、媒体分别断开。

### 4. WiFi 路：为什么可以直接走标准 WebRTC

WiFi 模式下，App 和板端处于同一个板端热点网段：

```text
客户端 WiFi 网卡：<CLIENT_IP>
板端无线接口：  <BOARD_IP>

本项目示例为客户端 `192.168.1.50`、板端 `192.168.1.1`。
```

板端服务应绑定在 `0.0.0.0` 或指定的无线接口地址，MediaMTX 配置还应明确告诉 ICE 使用 `<BOARD_IP>`：

```yaml
webrtcLocalUDPAddress: :8189
webrtcLocalTCPAddress: :8189
webrtcIPsFromInterfaces: false
webrtcAdditionalHosts: [127.0.0.1, <BOARD_IP>]
```

#### WiFi 路：控制与信令

```text
App WebSocket ws://<BOARD_IP>:8999/ws/device/
  └─ 直接到板端控制服务

App POST http://<BOARD_IP>:<BOARD_WHEP_PORT>/cam0/whep
  └─ 直接到板端 MediaMTX
```

App 发出的 `start_streaming_exposure` 等控制指令先通过 WebSocket 让板端启动视频管线；随后 WHEP 请求触发 MediaMTX 的 `sourceOnDemand`，MediaMTX 从本机 `rtsp://127.0.0.1:554/live/0` 拉取 H.264 源。

#### WiFi 路：视频媒体

```text
① App POST WHEP offer 到 `<BOARD_IP>:<BOARD_WHEP_PORT>`
② MediaMTX 返回 answer，candidate 通告 `<BOARD_IP>:<BOARD_WEBRTC_PORT>`
③ App 与板端完成 ICE 配对
④ MediaMTX 直接通过 wlan0 UDP :8189 发 RTP/H.264
⑤ App 的 WebRTC 原生模块接收、解码并显示
```

WiFi 模式没有以下中间层：

- 没有 `usb-webrtc-relay/server.mjs`；
- 没有主机 UDP `18189`；
- 没有 `board_webrtc_udp_tunnel` 参与媒体转发；
- 没有 ADB forward；
- 没有 SDP candidate 改写。

因此 WiFi 模式的媒体路径是标准的局域网 WebRTC，延迟和故障点都比 USB 路少。

### 5. 两条路最重要的差异

```text
共同部分：
  Sensor → VI → VPSS → VENC → RTSP :554 → MediaMTX → WebRTC → App

USB 只改变 MediaMTX 之后的网络出口：
  MediaMTX UDP :8189
    → board tunnel :18190
    → ADB USB
    → host relay :18189
    → `<EMULATOR_HOST_IP>`
    → App

WiFi 直接使用真实网络出口：
  MediaMTX UDP :<BOARD_WEBRTC_PORT>
    → 板端无线接口 `<BOARD_IP>`
    → 客户端地址 `<CLIENT_IP>`
    → App
```

这也解释了为什么同一个 App 可以在两条路之间切换：App 上层始终使用 `RTCPeerConnection + WHEP`，只需要更换 WHEP URL 和 ICE 可达地址；板端相机编码和 MediaMTX 配置不需要切换。

## 五、逐层拆解

### 第 1 层：Sensor → H.264 码流（板端）

画面从 IMX662 传感器出来，经过瑞芯微的硬件管线：

| 阶段 | 说明 | 源码位置 |
|---|---|---|
| Sensor 输出 | 物理阵列 1936x1100，默认裁切成 1920x1080 | `sensor_v4l2_fmt.c:317-322` |
| VI 通道 | 视频输入，尺寸跟随 sensor 当前窗口 | `CMOS662MC.cpp:669-670, 965` |
| VPSS | 视频处理子系统，chn0/chn1 | `CMOS662MC.cpp:710-711, 966` |
| VENC | H.264 硬件编码，CBR，GOP 30，30fps | `CMOS662MC.cpp:534-537, 973` |

**关键点**：这四层的宽高是**同一组变量**一路传下去的（`CMOS662MC.cpp:914-973`）。所以改 sensor 裁切窗口（`roi_set`），推流分辨率会跟着一起变——这也是 16:9 / 4:3 切换能生效的原理。

```c
// CMOS662MC.cpp:914-924  尺寸从 sensor 当前窗口读取
RK_U32 u32Width = 1920;
RK_U32 u32Height = 1080;
{
    uint32_t sensor_width = 0, sensor_height = 0;
    if (SensorGetFmt(&sensor_width, &sensor_height) == 0 && ...) {
        u32Width = sensor_width;   /* roi_set 后即为 ROI 尺寸 */
        u32Height = sensor_height;
    }
}
```

### 第 2 层：RTSP → MediaMTX（板端）

编码后的 H.264 先进本地 RTSP 服务（`rtsp://127.0.0.1:554/live/0`），再由 MediaMTX 转成 WebRTC。

板端配置 `/userdata/hjc_test/mediamtx.web.yml`：

```yaml
rtmp: false
hls: false
srt: false
webrtc: true
webrtcAddress: :8889                              # WHEP 信令 HTTP 端口
webrtcLocalUDPAddress: :8189                      # WebRTC 媒体 UDP
webrtcLocalTCPAddress: :8189                      # WebRTC 媒体 TCP
webrtcIPsFromInterfaces: false
webrtcAdditionalHosts: [127.0.0.1, <BOARD_IP>]   # ICE candidate 里通告的地址
paths:
  cam0:
    source: rtsp://127.0.0.1:554/live/0
    rtspTransport: "tcp"
    sourceOnDemand: yes                           # 有人看才拉流
    sourceOnDemandStartTimeout: 3s
    sourceOnDemandCloseAfter: 10s                 # 没人看 10 秒后停
    overridePublisher: true
    maxReaders: 0
```

注意 `sourceOnDemand: yes`：**没有客户端时板端不产流**。所以 App 第一次连接时，MediaMTX 要花点时间去拉 RTSP 源，这期间 WHEP 会返回 404——App 端为此做了重试（见第 5 层）。

### 第 3 层：UDP over TCP 隧道（核心难点）

这是整套方案最反直觉的地方。

**问题**：WebRTC 的媒体流是 UDP。但板子只有 USB 连着电脑，`adb forward` **只能转发 TCP**。所以标准 WebRTC 在 USB 场景下根本跑不通。

**解法**：板端跑一个隧道进程，把 UDP 包装进 TCP。

```
board_webrtc_udp_tunnel 18190 127.0.0.1 8189
                        │     └─────┬────┘
                        │           └── 目标：MediaMTX 的 UDP 端口
                        └── 自己监听的 TCP 端口
```

分帧协议非常简单——**4 字节大端长度前缀 + 原始 UDP 载荷**。主机侧对应实现（`server.mjs:57-80`）：

```js
function writeTunnelFrame(tunnel, message) {
  const header = Buffer.allocUnsafe(4);
  header.writeUInt32BE(message.length, 0);      // 4 字节长度
  tunnel.write(Buffer.concat([header, message])); // + 原始 UDP 包
}

function receiveTunnelFrames(client, chunk, key) {
  client.buffer = Buffer.concat([client.buffer, chunk]);
  while (client.buffer.length >= 4) {
    const size = client.buffer.readUInt32BE(0);
    if (size <= 0 || size > 65535) { /* 丢弃异常帧 */ }
    if (client.buffer.length < size + 4) return;  // 等后续数据
    const message = client.buffer.subarray(4, size + 4);
    client.buffer = client.buffer.subarray(size + 4);
    udpSocket.send(message, client.port, client.address);  // 还原成 UDP
  }
}
```

于是：`App 发 UDP → 主机 relay 收 → 加长度头走 TCP → 过 USB → 板端拆包 → 发 UDP 给 MediaMTX`，反向同理。

### 第 4 层：主机 relay 与 SDP 改写

主机侧 `tools/usb-webrtc-relay/server.mjs` 干三件事：

**(1) WHEP 信令反向代理**（`server.mjs:183-224`）
App 请求 `http://<EMULATOR_HOST_IP>:<RELAY_HTTP_PORT>/board-webrtc/cam0/whep`，relay 剥掉 `/board-webrtc` 前缀，转发到主机本地的 WHEP forward 端口（经 ADB 到板端 `<BOARD_WHEP_PORT>`）。

**(2) 改写 ICE candidate**（`server.mjs:149-166`）——**这是让整件事能跑通的关键**

MediaMTX 返回的 SDP answer 里，candidate 写的是设备侧地址（例如 `127.0.0.1`、`<BOARD_IP>`）。USB 模式下，模拟器里的 App 不一定能访问这些地址，所以 relay 把每条 UDP candidate 改写成 `<EMULATOR_HOST_IP>:<RELAY_UDP_PORT>`：

```js
const match = line.match(/^(a=candidate:\S+\s+\d+\s+)(udp|tcp)(\s+\d+)(\s+)(\S+)(\s+)(\d+)(\s+typ\s+host(?:\s+.*)?)$/i);
if (!match) return line;
if (protocol.toLowerCase() !== 'udp') return '';     // TCP candidate 直接删掉
return `${before}${protocol}${priority}${spaceBeforeAddress}${relayAdvertiseHost}${spaceBeforePort}${relayUdpPort}${after}`;
//                                                    ↑ 模拟器可达宿主机地址   ↑ relay UDP 端口
```

TCP candidate 被整条删除（返回 `''` 再 filter 掉），强制 App 只走那条能通的 UDP 路径。

**(3) UDP ↔ TCP 中转**（`server.mjs:130-146`）
在 `0.0.0.0:18189` 收 App 的 UDP，按来源 `address:port` 建立会话表，每个会话独立开一条 TCP 隧道。隧道没就绪时先排队（最多缓 64 个包），8 秒无活动的会话自动回收。

**为什么需要 `<EMULATOR_HOST_IP>`**：模拟器必须有一个能访问宿主机的网关地址。MuMu 当前示例是 `10.0.2.2`，其他模拟器、AVD 或真机环境可能不同，不能把这个地址写死到通用实现里。

### 第 5 层：App 侧 WHEP 客户端

代码在 `src/features/home/camera/services/whep-service.ts`，是一个精简的只收不发（recvonly）WHEP 客户端。

协商流程：

```
1. new RTCPeerConnection({ iceServers: [] })       // 不用 STUN/TURN，纯 host candidate
2. addTransceiver('video', recvonly)
   addTransceiver('audio', recvonly)               // 必须加！见下方注意事项
   createDataChannel('')                           // 也必须加
3. createOffer() → setLocalDescription()
4. POST offer 到 WHEP URL  (Content-Type: application/sdp)
5. 收 answer → setRemoteDescription()
6. 后续 ICE candidate 用 PATCH 补发 (trickle ICE)
7. ontrack → 拿到 MediaStream → 交给 RTCView 渲染
```

几个容易踩坑的设计，代码注释里都标了原因：

| 做法 | 原因 |
|---|---|
| 必须加 audio transceiver 和 data channel | MediaMTX 对"纯视频 offer"的应答方式不同，协商会卡死（`whep-service.ts:104-106`） |
| 不过滤 loopback candidate | 保留它们能让双方瞬间配对（`whep-service.ts:106-107`） |
| 必须用 PATCH 补发 candidate | 否则板端只能看到 offer 那一刻已有的少数 candidate，导致路径很差、大量丢包（`whep-service.ts:134-137`） |
| POST 要重试 ~1.8 秒 | `sourceOnDemand` 冷启动时 MediaMTX 返回 404，重试避免竞态（`whep-service.ts:272-302`） |
| 只有 `failed` 才重连 | Android WebRTC 握手中途会短暂报 `disconnected`，此时重连会掐死正常会话（`whep-service.ts:161-168`） |

## 七、两条通道是独立的

很容易混淆的一点：**控制和视频是两条完全独立的链路**。

| | 控制通道 | 视频通道 |
|---|---|---|
| 协议 | WebSocket (JSON) | WebRTC / WHEP |
| 端口 | 18999 → 8999 | 18787 → 18889 + 18189 → 18190 |
| 服务 | `net_server_test` | MediaMTX + tunnel |
| 内容 | 拍照、ROI、曝光、白平衡、状态轮询 | H.264 视频帧 |
| 心跳 | 每 3 秒 `HeartBeat`（板端 10 秒判死） | ICE 自带保活 |

所以会出现这些组合状态：

- **能连上设备但没画面** → 控制通道通了，WHEP 或媒体隧道断了（最常见：缺 `18889` / `18190` 转发）
- **有画面但按钮没反应** → 视频通了，控制 WebSocket 断了
- **首页"设备已连接"闪烁** → 控制 WebSocket 在重连（历史问题，已用 3 秒心跳修复）

## 九、最容易出问题的地方

### 1. USB 重新枚举导致 forward 全丢（最高频）

`adb forward` 是**主机侧的临时状态**，以下任一情况都会清空：板子重插拔、板子重启、ADB server 重启、MuMu 重启。

RV1106 在同时跑 ISP + H.264 编码 + 视频传输时功耗较高，USB 供电不足会触发欠压抖动，Windows 驱动断开重连，`transport_id` 递增——**forward 就全没了**。

> 实测记录：2026-08-18 单次调试过程中，同一块板 `transport_id` 从 4 → 7 → 11 → 12，共发生 4 次重新枚举，每次预览都立刻断开。

诊断方法：

```bash
adb devices -l          # 看 transport_id 有没有变大
adb forward --list      # 空的就是丢了
```

现象对照：

- 只缺 `18999` → App 显示"未连接设备"
- 只缺 `18889` → WHEP 返回 502，画面卡在"正在连接"
- 只缺 `18190` → 信令成功但一帧都收不到，ICE 最终 failed

### 2. relay 没启动或是旧实例

`lastError` 出现 `WHEP proxy: connect ECONNREFUSED 127.0.0.1:18889` 通常意味着 forward 丢了而不是 relay 坏了。注意 `lastError` 是**历史值**，不代表当前仍在失败——恢复 forward 后重新加载页面即可。

### 3. App 已耗尽 WebSocket 重连次数

日志出现 `WebSocket Exceeded max retries` 后，即使恢复了 forward，旧页面也不会自己活过来。需要重新进入页面 / Reload / 重启 App。

### 4. 改了 `.env` 但没重新打 bundle

`EXPO_PUBLIC_*` 是**构建期**注入的。改完 `.env` 必须重新加载 Metro bundle，热刷新不一定生效。

> 另注：debug 构建**不会**把 JS 打进 APK，它期望从 Metro 加载。如果 Metro 没连上，App 会回退到 APK 里那份**旧的** `assets/index.android.bundle`，表现就是"代码改了但界面没变"。确认方法是看 Metro 日志有没有 bundle 请求。

## 十、WiFi 模式实例配置与调试说明

> 本节使用当前项目的 `<BOARD_IP>=192.168.1.1`、`<BOARD_SSID>=SC311-USBTEST` 作为示例。通用原理请以前面的第三节为准；部署到其他设备时替换这些参数。

App 现在同时支持两条链路，在**设置 → Wi-Fi 设置 → 连接方式**里切换（自动 / USB / Wi-Fi）。

### WiFi 模式拓扑（比 USB 简单得多）

```text
板端 MediaMTX  192.168.1.1:8889  (WHEP 信令)
              192.168.1.1:8189  (WebRTC 媒体 UDP)
板端 net_server 192.168.1.1:8999  (控制)
        │
        │  板子自己的 AP：SSID SC311-USBTEST / 密码 12345678
        ▼
   手机 / 模拟器宿主机
        │
   App ─┴─ 控制:  ws://192.168.1.1:8999/ws/device/
        └─ 视频:  http://192.168.1.1:8889/cam0/whep
```

**WiFi 模式下不需要 relay、不需要隧道、不需要 adb forward、不需要改写 SDP。**

原因：板端 `mediamtx.web.yml` 里 `webrtcAdditionalHosts` 已经包含 `192.168.1.1`，
ICE candidate 通告的就是可直连的地址；而 UDP 在真实网络里本来就能走，
不存在 "adb forward 只转 TCP" 那个限制。

### 两种模式对照

| | USB 模式 | WiFi 模式 |
|---|---|---|
| 控制地址 | `10.0.2.2:18999` → forward → 板端 8999 | `192.168.1.1:8999` 直连 |
| WHEP 地址 | `10.0.2.2:18787/board-webrtc/cam0/whep` | `192.168.1.1:8889/cam0/whep` |
| 需要 relay | 是（18787 + UDP 18189） | **否** |
| 需要 adb forward | 是（三条） | **否** |
| 需要 SDP 改写 | 是（candidate 改成 10.0.2.2） | **否** |
| 掉线主因 | USB 重新枚举清空 forward | WiFi 信号 / 漫游 |

### 自动探测与回退

偏好为**自动**时：

1. 启动时并行探测两个 `/status`（各 2 秒超时），先回应的采纳
2. 控制通道断开后，**持续掉线超过 5 秒**才会重新探测
3. 探测有 5 秒节流，且探测期间不重入
4. **只有另一条链路真的回应了才切换**；都不通就留在原链路继续重连

第 2、3、4 条是为了防止误切：USB 重新枚举导致的 1-2 秒抖动很常见
（实测一次调试期间发生 4 次），不能让它把 App 弹到 WiFi 上去。

切换时走「断开 → 换地址 → 重连」，因为预览 effect 依赖 `connectionStatus` 和
`transport`（`native-camera-preview.tsx:161`），`closed → open` 会自动重建 WHEP 会话，
所以视频会跟着控制一起切，不会出现"控制在 WiFi、视频还在 USB"的半切换状态。

### 相关代码

| 文件 | 作用 |
|---|---|
| `src/features/home/camera/transport.ts` | 地址表、偏好持久化、并行探测 |
| `src/features/home/camera/config.ts` | 三个 URL getter，按当前链路解析 |
| `src/features/home/camera/client.ts` | axios 请求拦截器动态 baseURL |
| `src/features/home/camera/camera-store.ts` | `initTransport` / `switchTransport` / 断线回退 |
| `src/features/settings/components/transport-selector.tsx` | 设置页三档选择器 |

### 调试建议

排查问题时**先在设置里锁定具体链路**，不要用自动——自动模式下失败了分不清
是哪条链路的问题。锁定后现象唯一，好定位。

### 通用换板部署检查清单

换成另一块硬件时，不应只修改 App 里的一个 IP。建议按下面顺序检查：

1. **确认设备身份**：记录物理 ADB serial、无线 MAC 和固件版本；
2. **保证热点唯一**：每块同时工作的设备使用不同 SSID，避免多个设备都占用同一个网关地址；
3. **确认板端服务**：控制服务、RTSP、MediaMTX 和隧道进程均已启动；
4. **确认监听地址**：控制端口、WHEP 端口和 WebRTC 媒体端口应绑定到正确接口；
5. **确认 ICE 地址**：WiFi 模式把设备 LAN 地址加入 `webrtcAdditionalHosts`；USB 模式由 relay 把 candidate 改写为模拟器可达地址；
6. **确认 USB 映射**：USB 模式为目标 serial 建立控制、WHEP、隧道三条 forward；
7. **确认 App transport 配置**：自动模式探测两个地址，手动模式锁定目标链路；
8. **分别验证控制和视频**：先测 `/status` / WebSocket，再测 WHEP 预览，最后测试拍照；
9. **最后再测自动切换**：先证明 USB 和 WiFi 单独都能工作，再验证断线回退，避免把基础链路问题误判成自动切换问题。

## 十一、为什么开发阶段主要用 USB

设备通常可以开自己的热点或加入局域网；当 App 能直接访问 `<BOARD_IP>` 时，WiFi 模式使用标准 WebRTC，不需要隧道，也不需要改写 SDP。本项目当前板的示例地址是 `192.168.1.1`。

但 WiFi 方案在开发调试时有两个硬伤：

1. **WiFi 一断，adb 也跟着断**，没法在掉线时诊断板子
2. **信号质量直接影响画质**，排查问题时分不清是代码问题还是链路问题

USB 方案虽然多了隧道这一层，但控制通道稳定、带宽有保障、掉线原因单一（就是 forward 丢了），更适合开发阶段。**生产环境用 WiFi 直连**，两条链路 App 都已支持，见第六点五节。

## 十三、附：板端控制接口调用格式

排查时常需要绕过 App 直接调板子。注意**不是** `/指令名` 这种形式：

```bash
# 正确：命令名是 query 的第一个 token，走 /command
curl "http://127.0.0.1:18999/command?roi_set&x=240&y=0&width=1440&height=1080&timing=0"

# 等价写法（+ 会被解码成空格）
curl "http://127.0.0.1:18999/command?roi_set+x=240+y=0+width=1440+height=1080+timing=0"
curl -X POST --data-binary "roi_set x=240 y=0 width=1440 height=1080 timing=0" http://127.0.0.1:18999/command

# 特例：/status 是唯一被单独硬编码的路径
curl "http://127.0.0.1:18999/status"

# 错误：会返回 INVALID_PARAM，因为根本没进 dispatcher
curl "http://127.0.0.1:18999/roi_set?x=240&..."
```

分隔符是 `strtok_r` 的 `" \t\r\n&"`，空格和 `&` 都行，逗号不行（`command_dispatcher.c:326-330`）。

常用查询：

```bash
curl "http://127.0.0.1:18999/command?camera_state"   # 曝光/增益/拍照结果
curl "http://127.0.0.1:18999/command?ser_status"     # 当前 ROI 等
```
